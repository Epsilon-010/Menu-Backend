# Image cleanup — tracked uploads and background deletion (Celery + RabbitMQ)
Objective: no image ever stays orphaned in Cloudinary, and no API request waits for a Cloudinary delete.
Branch: `feat/image-cleanup` (Backend, from `feat/slice-4-catalog`) and `feat/redesign` (Menu-Frontend). Delivery: ask-on-risk. Runner: `uv run pytest` (Backend), `npm test && npm run typecheck && npm run lint && npm run build` (Menu-Frontend).

## Specs
- S1 Why (L1, L3): with direct browser uploads the file reaches Cloudinary before the API saves its `public_id`; a failed attach (network drop, expired session, deleted item, storage error) or a crashed process leaves an orphan. Cloudinary and Postgres share no transaction, so the fix is a tracked registry plus guaranteed cleanup (eventual consistency with compensation), keeping the direct signed upload that CLAUDE.md requires.
- S2 Registry: every signed `public_id` is recorded in Postgres (`image_uploads`, status `pending`) before the browser uploads. Attaching it to an item marks it `attached` in the same transaction as the item change, and only a `pending` id of the same tenant can be attached (a conditional UPDATE; this also closes the "two items share one image" race). Replacing, removing or deleting an item's image, or rejecting an upload (format/size), marks it `discarded` in the same transaction.
- S3 Cleanup: a background job deletes from Cloudinary every `discarded` image and every `pending` image older than `IMAGE_PENDING_TTL_MINUTES` (default 60), then forgets the row. A failed delete keeps the row for the next run. Batches are claimed with `FOR UPDATE SKIP LOCKED`. API requests never call Cloudinary's delete.
- S4 Queue (L4, L5): "para procesos en cola usaras celery o rabbitmq". Celery with RabbitMQ as broker (Redis is not an option as Celery broker: kombu[redis] requires redis<6.5 and the backend uses redis 8.1). The API asks for an immediate cleanup after a change (best effort: a broker failure is logged, never fails the request); Celery beat runs the same cleanup every 5 minutes as the safety net. Postgres, not the broker, holds what must be cleaned.
- S5 Frontend (L3): the browser-to-Cloudinary upload runs outside the panel's serial change queue; only the attach call is queued, so a slow upload no longer blocks other edits.
- S6 Docs (L6): "no ovlides docuemtnar o cambiar por si abr otra sesion y no tiene conetxto de esto igual usa egram para la memoria" — CLAUDE.md (images, background jobs, Docker, commands, current state), `.env.example`, this document and Engram.
